<objective>
Build the Phase 1 diagnostic instrument: one shared `event-logger.sh` that appends a single JSON line per Claude Code hook event to `~/.claude/hook-events.log`, registered on every hook event the current docs list, installed by the existing `hooks/install.sh` mechanism without disturbing the auq-lock / working-lock hooks that keep the monitor working today.

Purpose: the whole Phase 1 verdict rests on being able to see what actually fires. Guessing from docs is exactly what this refactor exists to stop doing — RESEARCH.md found the same docs page reporting two different field names for the same event on two fetches. The log is ground truth; this plan builds the thing that produces it.

Output: `hooks/event-logger.sh`, `hooks/hook-events.json` (the canonical event list), an extended `hooks/install.sh` with matching `--remove-logger` teardown, and `test_event_logger.py` covering both the logger and the merge.

Decision map (CONTEXT.md locked decisions, cited in tasks below):
- **D-01** Instrument, don't guess — log every event; no state-derivation logic in this phase.
- **D-02** Non-invasive — install alongside the existing hooks, same bash+jq+settings.json mechanism, existing behavior unchanged.
- **D-03** Register on every hook event type Claude Code supports (resolves RESEARCH.md Open Question #1 in favour of ALL documented events — a subset would bias the verdict).
- **D-04** Append-only JSONL on the shared `~/.claude` mount, safe under concurrent writers (single short O_APPEND line).
- **D-05** The live matrix run is user-assisted UAT — out of scope here (plan 01-02 delivers the runbook).
- **D-06/D-07** Verdict lives in TEST-MATRIX.md — out of scope here (plan 01-02).

Hard boundary for this plan: **never run `hooks/install.sh` against the real `$HOME`.** This agent runs inside the user's live container with the real bind-mounted `~/.claude`; mutating it would change the user's running monitor mid-session. Every verification runs with `HOME` pointed at a `mktemp -d`. The real install is step 1 of the UAT runbook, performed by the user deliberately.
</objective>

Wire the single thinnest path all the way through: repo script -> install.sh merge -> settings.json command string -> execution against a payload -> a line in the log. Register exactly ONE event (`Stop`) for now; task 2 widens the list. This is production code, not a spike — the script written here is the one that ships.

Create `hooks/event-logger.sh` (mode 0755, `#!/usr/bin/env bash`) per D-01 and D-04:
- Header comment explaining it is a diagnostic-only Phase 1 instrument that never emits decision-control stdout and never fails a session, and naming `hooks/install.sh --remove-logger` as the teardown.
- Read stdin exactly once into a variable (hooks get one shot at stdin — the pattern `auq-lock.sh` already follows). If it is empty, exit 0.
- Build the output line with a SINGLE `jq -c` invocation over that payload. Object shape, in this order: `ts` (ISO-8601 UTC, `now|todate`), `ts_ms` (`now*1000|floor`, needed because matrix cases #2 and #5 turn on sub-second event ordering), `event` (`.hook_event_name`), `session_id`, `cwd`, `keys` (the payload's own top-level key names — this is what resolves the doc paraphrase risk in RESEARCH.md A2/Pitfall 1 without logging any values), then the scalar metadata fields present in this slice: `tool_name`, `stop_hook_active`. Strip null-valued entries with `with_entries(select(.value != null))`.
- Append the resulting single line to `$HOME/.claude/hook-events.log` with `>>`, creating the parent dir if needed.
- Exit 0 on every path. Choose shell options so that a failed `jq` parse, a missing field, or a false conditional cannot make the script exit non-zero — a conditional written as a bare `test && action` compound as the last statement of a block is a known way to leak a non-zero status under `set -e`; use explicit if-blocks instead.
- Parse stdin only through `jq`. Do not interpolate any payload-derived text into a shell command string and do not hand payload text to the shell for interpretation (ASVS V5 / threat T-01-01).

Create `hooks/hook-events.json` containing a JSON array with the single element `"Stop"`, plus nothing else. This file is the canonical registration list; task 2 fills it out.

Extend `hooks/install.sh`:
- Install `event-logger.sh` into `$CLAUDE_DIR/hooks/` alongside the two existing scripts, with the same `install -m 0755` + echo pattern.
- **Fix the early-return trap first:** today the "no settings.json yet" branch does `cp "$SNIPPET" "$SETTINGS"` then `exit 0`, which would skip logger registration entirely on a fresh install. Restructure so that branch seeds settings.json from the snippet and then falls through to the registration step below, instead of returning early. The existing lock-merge jq block must still be skipped on that path (the snippet already is the canonical lock set).
- Add a second, separate jq invocation after the existing lock merge that registers the logger. Keep it separate from the existing block so the current merge stays byte-for-byte the behavior it has today (D-02). Drive it off `hooks/hook-events.json` with `--argjson`, and pass the logger command string with `--arg` so no escaping games are needed. It must `reduce` over the event list, and for each event name: take `.hooks[$event] // []`, drop any group whose `.hooks[]?.command` matches `event-logger\.sh` (same `has_cmd` idempotency idea the file already uses), then append one matcher-less group containing `{type: "command", command: <logger cmd>, timeout: 2}`. Matcher is omitted deliberately — an omitted matcher fires on every occurrence of that event, which is the point.
- The logger command string is `bash "$HOME/.claude/hooks/event-logger.sh"` with `$HOME` left literal and unexpanded in the JSON, matching how the existing entries are written in `settings-snippet.json`.
- Route the logger merge through the same safety path the file already uses: write to `$SETTINGS.tmp`, validate with `python3 -c "import json; json.load(...)"`, then `mv`. The timestamped `.bak` copy taken before the lock merge covers both steps.
- `timeout: 2` matches the existing hooks. `PreToolUse` gates every tool call, so the script must stay cheap: one `jq`, one append, no loops.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Claude Code process -> hook script stdin | The JSON payload is untrusted-shaped input: field presence, types, and size are all outside this repo's control, and its values carry whatever the user typed and whatever files were read. |
| Hook script -> shared `~/.claude` bind mount | `hook-events.log` lands on a directory mounted from the Windows host and shared by every container on it — readable outside the writing container, and writable concurrently by several. |
| install.sh -> `~/.claude/settings.json` | A single shared config file that drives the hooks of every container on the host; a bad write degrades live monitoring globally, not just for this session. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-01 | Tampering | `hooks/event-logger.sh` stdin handling | high | mitigate | Payload is parsed only by `jq`; no payload-derived text is interpolated into a command string or handed to the shell for interpretation. Task 1 action states the rule; task 2's gate asserts it against a comment-stripped read of the script. |
