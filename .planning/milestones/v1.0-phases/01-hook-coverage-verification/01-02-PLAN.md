Create `.planning/phases/01-hook-coverage-verification/01-UAT.md`.

**Opening section — what and why.** State that this is a one-off diagnostic run for Phase 1, that the logger is temporary and gets removed at the end, and that its output is the ground truth the hybrid verdict is derived from. Note the two safety facts from RESEARCH.md Pitfall 2 that the tester needs to know before starting: the log lives on the shared `~/.claude` mount and is visible from Windows, and the default field set deliberately excludes tool inputs, tool outputs, prompt text, and assistant message bodies — so it is safe to run during ordinary work, and `GREENLIGHT_LOG_RAW=1` should only be exported for a short, deliberate window if a raw schema dump is needed for a specific case.

**Setup section — numbered, copy-pasteable.** (1) Run `bash hooks/install.sh` from the repo inside a container. (2) Confirm registration actually landed by counting logger entries in `~/.claude/settings.json` against the length of `hooks/hook-events.json` — a case that looks silent because its event was never registered is the failure mode this step exists to rule out. (3) Restart any Claude Code sessions that were already running, since settings.json is read at session start. (4) Record the Claude Code version (`claude --version`) — it goes in every Verified-column entry, because the whole premise of this project is that these behaviors move between versions. (5) Truncate `~/.claude/hook-events.log` so the run starts clean. (6) Open a follower on the log in a second terminal; give both a raw `tail -f` and a readable `jq -c` variant projecting the fields that matter most.

**Case-marker helper.** Give a one-line shell function the tester defines once, which appends a marker line to the log carrying the case number and a millisecond timestamp. Run it immediately before each case. Since the log is shared across containers and concurrently written, markers are what make a case's lines unambiguously separable afterwards — and they also let the tester diff wall-clock time against the `ts_ms` of the events, which is what case 2 turns on. Give the matching extraction command: print everything between the marker for case N and the next marker.

**Per-case sections.** One section per case, headed exactly `### Case N — <short title>` with N from 1 to 21 matching TEST-MATRIX.md's row numbers exactly. Each section carries four labelled parts: **Trigger** (expanded from the matrix's "How to trigger" column into something unambiguous), **Observe** (the exact command to run against the log — prefer a `jq -c 'select(...)'` filter over the case's marker window), **Pass condition** (what the tester is looking for, in terms of which events appeared, in what order, and with which field values), and **Record** (what to put in the Verified column).

Write all 21. These need explicit handling beyond the matrix's own notes:

- **Case 2 (normal turn end):** the point is whether `Stop` fires after terminal rendering finishes. Have the tester note wall-clock time at the moment the reply looks finished on screen and compare against that event's `ts_ms`. This is the case that decides whether the debounce idea in NOTES.md is dead — say so.
- **Case 3 (long multi-tool turn):** the observable is the largest gap between consecutive events for the session, not any single event. Give a command that prints consecutive `ts_ms` deltas so the tester can read the worst gap directly — that number is what a heartbeat window has to tolerate.
- **Case 4 (permission prompt):** run it for more than one shape of prompt (a Bash command, a file write, an MCP tool if available) and record whether the fields differ between them, since Phase 2 needs to key `needs_input` off something stable.
- **Case 5 (permission answered):** run both the approve and the deny path. Deny executes no tool at all, so record what, if anything, marks the resumption.
- **Case 6 (AskUserQuestion):** state at the top of the section, before the trigger, that **Expected: ZERO log lines** — confirming the silence *is* the pass. Cite the sources from RESEARCH.md (anthropics/claude-code issues 28273, 12605, 15872). The only thing the live run adds is confirming it still holds on the tester's installed version. Note the corollary: if it holds, auq-lock stays as the `needs_input` fallback in Phase 2.
- **Case 8 (Esc interrupt):** same shape — **Expected: ZERO log lines** for the interrupt itself, per the official docs statement and issue 9516. Include the "yuno" variant from the matrix (Esc right after a foreground agent returns). Note what this implies: something other than `Stop` has to clear a stale working state.
- **Case 12 (foreground subagent):** the thing being verified is that the subagent's end event is *distinguishable* from a real turn end. Have the tester record both the subagent event and the eventual real `Stop`, with their `ts_ms`, so Phase 2 can prove it will ignore the former.
- **Case 13 (background task completes and re-invokes Claude):** this is the one genuinely open question no desk research resolved (RESEARCH.md Open Question 2). Have the tester watch specifically for `TaskCreated`, `TaskCompleted`, `PostToolBatch`, `SubagentStart`, and `SubagentStop` in addition to the classic events, and record the full ordered event sequence for the whole episode rather than a yes/no. If nothing at all fires, that is itself the finding.
- **Cases 9, 19, 21 (killed container / abandoned prompt / hookless container):** absence of events is expected by construction. Make the Record instruction be "the last event seen and its `ts_ms`", since what Phase 2 needs from these is how long the silence runs before the situation is detectable, not whether an event exists.
- **Case 15 (multi-container):** add an explicit check for interleaved or truncated lines — run `jq -c . ` over the whole log and count lines that fail to parse. Per RESEARCH.md Pitfall 5 and assumption A1, any interleaving observed here is a **real finding about this host's bind mount** to record in the verdict, not a logger bug to work around. Note that `session_id` is what separates concurrent sessions, and confirm `cwd` is populated per session since Phase 2's label mapping depends on it.
- **Case 17 (turn ends with async work in flight):** flag it as a design question, not only a detection question — if `Stop` fires while a background shell is still running, hooks-only would notify early, which contradicts the current grey-while-working semantics D-07 says to preserve. Record what fires and note that the decision itself belongs to Phase 2.
- **Case 18 (badges):** record whether any event carries a shell or task identifier in a *scalar* field. The logger does not capture tool inputs and outputs by value, so use the `keys` array to determine whether the payload carries the identifiers at all — that answers the V2-01 question without ever writing tool payloads to disk.
- **Case 20 (corrupt state file):** in Phase 1 there are no state files yet, so scope this case to what is observable now: hand-append a truncated line to `hook-events.log` and confirm the readable-log workflow in this runbook tolerates it. Record it as a note carried forward to Phase 2's ENG-04 rather than as a hook-coverage finding.

**Recording section.** State the exact Verified-column format so entries are comparable: date, Claude Code version, and outcome, e.g. `2026-07-28 / cc 2.1.x / Stop fired, ts_ms 340ms after perceived render end`. Say that "no event" is a valid and valuable outcome and must be written explicitly rather than left blank — a blank cell is indistinguishable from a case that was never run.

**Verdict section.** Point at TEST-MATRIX.md's "Verdict to extract" template (updated in task 2) as the place the verdict is written, per D-06 — explicitly no separate report file. Restate the three questions it answers and the D-07 requirement that every hook-silent case names a concrete fallback from the available set: the existing auq-lock, shell_tracker, a targeted jsonl peek, or the `docker ps` cross-check.

**Teardown section.** Run `bash hooks/install.sh --remove-logger`, delete `~/.claude/hook-events.log`, and restart sessions. Say plainly that this is mandatory rather than optional: the log's bounded lifetime is what makes writing diagnostics to a shared, Windows-visible mount acceptable in the first place (threat T-01-02).
