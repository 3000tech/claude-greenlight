<objective>
Put shadow mode into real usage on the machine that matters, and prove the two things this
sandbox structurally cannot: that the user sees no change at all, and that the divergence
log is filling with records worth reviewing.

Purpose: every test in this phase runs against synthesised payloads on a local filesystem
with no Docker. The three facts the Phase 3 flip will rest on — the rename is atomic on the
9p mount, `docker inspect` reports the status enum this engine branches on, and the overlay
is genuinely unchanged — exist only on the user's Windows + WSL2 + Docker setup. Phase 1
established exactly this working model with `01-UAT.md`; this plan is its Phase 2
counterpart.

Output: `02-UAT.md` and a confirmed live shadow-mode installation.
</objective>

Write `02-UAT.md` following `01-UAT.md`'s structure. Ground every command in the code as it
shipped: read the actual script and the actual engine first and derive each observation
command from them. Phase 1's runbook was written this way deliberately, and that is why its
live campaign spent no session time debugging commands referencing fields the instrument
never emitted.

**Preamble.** State what shadow mode is, that the overlay keeps rendering the legacy
verdict throughout, and that this runbook's job is to confirm the absence of change plus
the presence of a filling divergence log — not to decide the flip.

**Setup.** Pull the repo inside one container, run `hooks/install.sh`, and give the exact
command that confirms the state writer is registered on every event in
`state-writer-events.json` while the working-lock, auq-lock and event-logger entries are
still present at their previous counts. Restart the Windows monitor. Give the command that
confirms `~/.claude/monitor-state/` fills with one file per live session and that
`~/.claude/monitor-divergence.log` exists.

**Section A — zero visible change (D-01).** A short, honest checklist to run across an
ordinary hour of work: labels identical, the grey-to-green flip feels the same, the toast,
the audio and the Telegram push still fire on the same events with the same wording, the
badges look the same, and a session that ends still disappears the same way. Anything that
looks different is a defect to report — including anything that looks better.

**Section B — the two environment assumptions.** One case running the container-status
inspect command against a running container, then the same container paused, then a stopped
one, recording the three literal strings returned; this is the only way to confirm the enum
the engine branches on. One case for atomicity: start a turn, kill the container mid-write,
then confirm every file under `monitor-state/` still parses as complete JSON and that no
partially-written temp file is being picked up as a session.

**Section C — the hook-silent cases.** One numbered case each for the Esc interrupt, a
permission prompt that is denied, a killed container, a paused-then-unpaused container, an
abandoned pre-tool prompt, a container running an image with no hooks installed, and two
containers mounting the same `/workspace` at once. For each: the trigger, what the state
file should show, roughly how long until the staleness window resolves it, and what the
divergence log should and should not contain. Quote the real constant values for the
windows rather than approximating them in prose.

**Section D — the diagnostic mode.** How to run the monitor in state-files mode for a
hands-on look at the new engine's own view, including the operational detail that the
normal monitor must be closed first because of the process singleton, and a note that
badges in this mode preview the single background-task signal rather than reproducing
today's pair.

**Section E — the divergence review protocol.** State plainly how review works: the user
does not read the log, Claude does, in-session, with the user (D-02). Give the jq triage
commands — count records by verdict pair, list the distinct last-event values involved,
show the longest episodes — using the field names `monitor.py` actually emits. State the
three classifications a divergence can receive during that conversation (legacy-wrong,
hooks-wrong, both-defensible) and note explicitly that a divergence where the hook engine
is the correct one is a finding worth keeping, not a regression. State the cadence: roughly
a week of real usage, the exact number agreed when reviewing, and no automatic flip (D-03).

**Section F — the lock hooks (SW-03).** A short pass confirming that with the state writer
installed alongside them, an AskUserQuestion modal and a tool-permission prompt still turn
the overlay green through the existing auq-lock path, and a long tool still holds it grey
through the existing working-lock path — the legacy mechanisms are still the ones driving
the screen and must be unaffected.

**Teardown.** The one-command rollback `hooks/install.sh --remove-state-writer`, plus
deleting `~/.claude/monitor-state/` and the divergence log, and a note that working-lock
and auq-lock stay installed either way because they remain load-bearing until Phase 3.

**Recording format.** A small table the tester fills in per case, matching `01-UAT.md`'s
convention (date, Claude Code version, outcome), so results fold back into `TEST-MATRIX.md`
and into Phase 3's flip decision.
