authoritative for a whole session lifecycle, including the three cases the live campaign

stops after its parent, and a `Stop` that fires while background work is still running.

Branches to add in this task:

`UserPromptSubmit` resolves `working`. This is the prompt-to-first-tool bridge; TEST-MATRIX
case 13 confirmed a background task re-invoking Claude also emits it, so a re-invoked turn
is visible from its first instant with no extra branch.

`PostToolUse`, `PostToolUseFailure` and `PostToolBatch` all resolve `working` — these are
the heartbeat events, and every one of them re-stamps `ts`/`ts_ms`, which is what the
engine's staleness window reads. `PostToolUseFailure` carries `is_interrupt` and
`duration_ms`, but TEST-MATRIX case 8 showed an Esc interrupt emits no event at all, so
those fields are not load-bearing for the state and must not be read into the record.

`PermissionRequest` resolves `needs_input`. Case 4 measured it as instant, roughly six
seconds ahead of `Notification`, and case 6 showed the AskUserQuestion modal emits it too —
so this one branch covers both the permission prompt and the AUQ modal that `auq-lock.sh`
exists for today.

`Notification` also resolves `needs_input`, matching what `auq-lock.sh` does today for any
notification type. D-08 demotes it to secondary, not to absent: it is the fallback for any
notification type `PermissionRequest` does not front-run.

`SessionStart` resolves `idle` when its `source` field is `startup`, `resume`, `clear`, or
absent/unrecognised. When `source` is `compact` the branch exits 0 without writing
anything: TEST-MATRIX case 11 confirmed `/compact` re-fires `SessionStart` with the SAME
session_id mid-session, and writing `idle` there would blank a live `working` state and
read downstream as a turn that ended.

Leave `Stop`, `SubagentStop` and `SessionEnd` for Task 2 — a `Stop` payload must keep
producing `waiting` exactly as the tracer left it while this task lands.

Note in the script's header comment that `idle` is an internal writer state with no
separate rendering: the engine maps it to the same WAITING verdict as `waiting` and
`needs_input`, per D-07 and D-01.

that file byte-for-byte unchanged, and a test that an unregistered/unknown event name
writes nothing. Extend `_payload` so a `source` value can be supplied.

Complete the mapping with the three turn-end branches.

`Stop` resolves `waiting` when `background_tasks_count` is zero and `working` when it is
greater than zero. This is the hook-native replacement for today's shell_tracker-driven
grey-while-async-work behaviour: TEST-MATRIX case 17 recorded a `Stop` firing at 13:02:38
with a background task still alive until 13:03:02, and the user confirmed live that the
overlay stayed grey for the whole window — that is the semantics to reproduce, and the same
`Stop` payload carries the signal to reproduce it with. Resolve the count once, before the
state, and use the same value for both the gate and the record's
`background_tasks_count` field, so the number the future unified badge reads (D-09) and the
number that gates the verdict can never disagree.

Confirm the count expression treats a missing `status` as still-running and only excludes
`completed` and `failed` — RESEARCH assumption A2 asks for that deny-list rather than an
exact-match allowlist so an undocumented status value cannot silently undercount live work.
An absent `background_tasks` array yields 0.

`SubagentStop` exits 0 without writing anything. This branch has to exist and has to be
explicit: TEST-MATRIX case 12 recorded `SubagentStop` arriving two to three seconds AFTER
the parent's `Stop` on two occasions, so any write here would move the verdict after the
turn already ended — that is the historical premature-transition bug this phase must not
reintroduce. The event stays registered precisely so this no-op is exercised and asserted
rather than left to the absence of a branch.

`SessionEnd` removes `"$state_dir/$sid.json"` with `rm -f` and exits 0, unconditionally,
for every `reason` value. Case 10 (`reason=resume` on the ten-second picker session), case
11 (`reason=clear` on the retired session_id) and case 14 (`reason=prompt_input_exit` on a
clean exit) are all served by the same unconditional removal, which is what keeps
`monitor-state/` from accumulating orphans. Do not gate the removal on any other check.
`docker kill` emits no `SessionEnd` at all (case 9), so a killed session's file is left to
age out of the engine's window — that is the staleness path, not this one.

In `test_state_writer.py`, extend `Goal5_EventToStateMapping` and add
`Goal6_TurnEndSemantics`: a `Stop` with an empty/absent `background_tasks` array produces
`waiting`; a `Stop` with one entry whose status is `running` produces `working` and
`background_tasks_count` of 1; a `Stop` with one `completed` and one `failed` entry
produces `waiting` and a count of 0; a `Stop` with an entry that has no `status` key at all
produces `working` and a count of 1; a `SubagentStop` fired against a state file that says
`waiting` leaves it byte-for-byte unchanged; a `SessionEnd` removes the file for each of
`prompt_input_exit`, `resume` and `clear`; and a `SessionEnd` for a session with no state
file exits 0 without error. Add one assertion that no field of the `background_tasks`
entries themselves (their ids, descriptors or command text) appears anywhere in the written
state file.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Claude Code → hook script stdin | Untrusted-shaped JSON payload, now including a `background_tasks` array whose entries can carry command text |
| `install.sh` → the user's live `~/.claude/settings.json` | A jq pipeline rewrites the file that controls every hook on the machine |
| Hook script → Claude Code control flow | The mapping now covers `PermissionRequest`, `PostToolBatch`, `Stop` and `SubagentStop`, every one of which can block or deny on a bad exit code or stray stdout |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-07 | Information Disclosure | `background_tasks` entries read by the `Stop` branch | high | mitigate | The array is reduced to a count inside the jq pipeline; no entry field is ever selected into the record, asserted by a test that descriptive text from the payload does not appear in the written file |
| T-02-08 | Tampering / Denial of Service | New branches on `PermissionRequest`, `PostToolBatch`, `Stop`, `SubagentStop` | high | mitigate | Every added branch ends in `exit 0` with no stdout, including the deliberate no-op and the removal path; the existing empty/malformed-payload tests keep asserting silent exit 0 |
| T-02-09 | Tampering | `--remove-state-writer` rewriting `settings.json` | high | mitigate | Timestamped backup before mutation, `python3 -c json.load` validation of the candidate file before the `mv`, and a jq filter scoped to commands matching the state-writer script name only |
| T-02-10 | Denial of Service | Teardown crashing jq on a `settings.json` with a null `hooks` key | medium | mitigate | Reuse `--remove-logger`'s null guard; regression test installs the `{}` case explicitly |
| T-02-11 | Tampering (data loss) | Removal sweep clobbering unrelated or third-party hook entries | high | mitigate | The filter selects on the state-writer command string only; tests assert the event-logger count, the lock counts, an unrelated top-level key and a third-party hook entry all survive |
| T-02-SC | Tampering | npm/pip/cargo installs | high | accept | Zero new external packages this phase (RESEARCH.md Package Legitimacy Audit: not applicable); no install task exists to gate |
