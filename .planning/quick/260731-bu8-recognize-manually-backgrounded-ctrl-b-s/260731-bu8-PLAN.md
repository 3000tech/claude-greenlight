<objective>
Make the ⚙ background badge light for shells the user backgrounded by hand.

Claude Code has two ways for a Bash command to end up in the background. Claude can start
it that way (`run_in_background`), and the user can promote a running foreground command
with Ctrl+B. The two paths write different tool_result markers, and `shell_tracker.py` only
knows the first one — so `has_active_shells()` returns False for a Ctrl+B shell and the
overlay shows no badge while the terminal itself is reporting a live shell. Verified live
today (2026-07-31, cc 2.1.220+): the record is present in the jsonl, the badge is dark.

Termination already works for both paths: Claude Code emits the same
`<task-notification>` with `<task-id>` and `<status>` whichever way the shell was
backgrounded, and the existing pattern matches any id. So the entire defect is on the start
side, and the entire fix is teaching start detection about the second marker.

Purpose: the badge is the monitor's answer to "is something still running in that session?".
A badge that is right for Claude-started shells and silently wrong for user-started ones is
worse than no badge, because the user learns to distrust it.

Output: a widened start pattern in shell_tracker.py plus three regression tests grounded in
a real captured session record (live badge on, badge off after completion, no spoofing from
escaped echo).

Scope note: this touches legacy jsonl parsing only. Since quick 260731-an2 rev.2,
`has_active_shells` feeds only the ⚙ badge and the divergence evidence string — never the
WORKING/WAITING decision — so this change cannot move any status verdict, in either engine.
</objective>

1. The start record — a `user` record whose `message.content` is a one-element list holding
   a tool_result block, with keys in this order: `tool_use_id`, `type`, `content`,
   `is_error`. Note `tool_use_id` comes BEFORE `type`; the existing anchor still holds
   because it only requires a brace-free span FROM the type key TO the content key. The
   same record carries a top-level `toolUseResult` object with `backgroundTaskId` and
   `backgroundedByUser: true` — useful documentation of intent, but not what the parser
   keys off.
2. The completion record — a `queue-operation` record (not a user message) whose `content`
   string is the `<task-notification>` block. Between `</task-id>` and `<status>` it carries
   `<tool-use-id>` and `<output-file>` lines, roughly 180 characters — comfortably inside
   the 800-char gap the existing notification pattern allows.
3. A false-positive candidate seen in the same file — a LATER tool_result whose content is
   a grep/cat echo of the jsonl itself. Its own content string starts with fragment text,
   and every inner quote is escaped (`\"type\":\"tool_result\"`), so neither the outer nor
   the inner form can satisfy a pattern that requires unescaped quotes immediately around
   the key names. This is the concrete reason the anchoring exists, and task 2 turns it
   into a test.
