<objective>
Stop a never-ending background shell from pinning a session grey forever. In `scan()`,
`has_active_shells()` is one of the conditions that force WORKING; a dev server started
with `run_in_background` never terminates, so `has_bg` stays true for the rest of the
session's life and the overlay never goes green even when Claude has been idle for hours.
The user currently works around this with `nohup`.

The pin itself is correct for the case it was built for: while a finite bg task (build,
test suite, long install) is running, grey means "Claude will resume on its own, don't
come" — and it will, because task completion re-invokes Claude with a UserPromptSubmit
(TEST-MATRIX case 13). So the fix is a time cap, not a removal: the pin holds only while
the session's jsonl is still fresh; once the file has been silent past the cap, the
process is an eternal one (dev server, watcher) and the semaphore is free to go green
while the badge keeps showing the running process.

Purpose: the monitor's whole job is "this session needs you now". A permanently grey row
is the same failure as a permanently green one — the signal stops meaning anything, and
the user starts routing around the tool.

Output: a module-level `BG_PIN_MAX_SEC` cap applied to the status decision only, four
regression tests locking the behaviour down, and a note in TEST-MATRIX so the identical
cap is carried into the hook-native rule when Phase 3 flips the default engine.
</objective>
